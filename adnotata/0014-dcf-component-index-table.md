# 0014 — DCF component index table & growth semantics

The unlock that unblocks size-changing component writes. Companion
to `0013-dcf-outer-format.md`; resolves the "where does Dyalog
encode the active block offset?" question that left the size-
changing path stuck.

Recorded purely from synthetic fixtures generated by gritt
(host-side; the inner-claude orchestration produced no usable
strace data). No real-world DCF bytes here.

## Method

Two paired fixtures, byte-diffed:

- `/tmp/orig.dcf` — Dyalog-written from scratch with a single
  namespace component `ns ← ⎕NS'' ⋄ ns.x ← 42`.
- `/tmp/grown.dcf` — `cp` of the above, then opened by Dyalog and
  the component overwritten via `⎕FREPLACE` with a strictly larger
  namespace `(x: 42 ⋄ y: 99 ⋄ z: 'longer string member to force
  component growth')`.

Result: orig 3024 bytes, grown 5296 bytes. The diff isolates the
fields Dyalog updates when a component grows.

## Finding: the component index table

`header[0x18]` is the offset of a per-component block-offset table:

```
header[0x18] : u64 LE   →   file offset where the table starts
```

The table is an array of u64 LE block offsets indexed by component
number:

```
table[i]  =  *(u64*)(file + header[0x18] + i*8)
          =  byte offset of the active block for component i
table[0]  =  0       (sentinel — components are 1-indexed)
table[i]  =  0       for components that don't exist
```

**This is the field Dyalog consults to find the live block.**
`header[0x58]` was previously misread as a component pointer — it
holds the offset where blocks *first* started in this file (always
`0x100` for a newly-created file), not where any individual
component currently lives.

### Confirmation from a 2-component fixture

```
tie ← '/tmp/two.dcf' (⎕FCREATE⍠1) 0
'first' ⎕FAPPEND tie      ⍝ becomes component 1
(⍳7)    ⎕FAPPEND tie      ⍝ becomes component 2
```

Header reads:

| Field           | Value    |
|-----------------|----------|
| `header[0x18]`  | `0x138`  |
| `header[0x28]`  | `0x1f0`  |

Table at `0x138`:

| Index | Offset at | Value (block offset) |
|------:|-----------|----------------------|
| 0     | `0x138`   | `0`                  |
| 1     | `0x140`   | `0x100`              |
| 2     | `0x148`   | `0x1b8`              |
| 3     | `0x150`   | `0`                  |

The block at `0x100` is the `'first'` component, the block at
`0x1b8` is the `(⍳7)` component. The table layout is exactly what
the model predicts.

### Confirmation from the grown fixture

Component 1 in `orig.dcf`:

| Field                       | Value           |
|-----------------------------|-----------------|
| `header[0x18]`              | `0x908`         |
| `header[0x28]` (prim_tail)  | `0x988`         |
| `table[1]` at `0x910`       | **`0x100`**     |

Component 1 in `grown.dcf` (after `⎕FREPLACE` made it larger):

| Field                       | Value           |
|-----------------------------|-----------------|
| `header[0x18]`              | `0x908`         |
| `header[0x28]` (prim_tail)  | `0x1220`        |
| `table[1]` at `0x910`       | **`0x988`**     |

The table entry moved from `0x100` to `0x988`. The live block was
relocated to the old primary tail and the table entry updated to
match.

## What growth looks like at the byte level

Dyalog's `⎕FREPLACE`-grows-a-component sequence:

1. **Don't touch the old block contents in place.** The old block
   at the original offset stays where it is, but is converted into
   a "placeholder/free" block:
   - The block's `size` field is rounded up to absorb the trailing
     padding that used to sit between block-end and primary-tail
     (e.g. orig block ended at `0x8F0`, padding ran `0x8F0..0x908`;
     placeholder size becomes `0x808` so the block now ends at
     `0x908`).
   - The block magic at `+0x04` is zeroed; the build code,
     timestamp, hash, type_rank, shape are all zeroed too. Only
     the size field and a couple of inert metadata fields (`+0x10`
     = `2`, `+0x20` = `2`) survive. This makes it clearly not a
     live block to anyone scanning by magic.
2. **Append the new block at the old `primary_tail`.** In the
   grown fixture, the new block starts at `0x988` (= the old
   `primary_tail`). Block header layout is identical to a freshly-
   written block:
   - `+0x00`: new block size (e.g. `0x880`)
   - `+0x04`: magic `a4 14 0e a4`
   - `+0x0C`: build code (`0x1f5` = 501)
   - `+0x10`: a new timestamp (differs from the original — Dyalog
     stamps the modification time)
   - `+0x14`: a content-dependent hash (`b8 88 00 00` in the grown
     fixture, vs `d0 3c 0c 00` in the original)
   - … then the 220⌶ body, exactly as for a fresh component.
3. **Update the file header**:
   - `header[0x28]`, `[0x30]`, `[0x50]` all rewritten to the new
     `primary_tail = new_block_offset + new_block_size + footer`
     (= `0x1220` here).
   - `header[0x60]` is a content-dependent hash that changes
     (`9fdb a003` → `921a b7ba`). Likely a CRC over header bytes.
   - `header[0xa8]`, `[0xb0]` are timestamp + content-hash that
     also change.
   - `header[0x18]` (table offset) stays unchanged — the table
     was sized large enough at creation time and isn't relocated.
4. **Update the table entry** for the affected component:
   `*(u64*)(file + header[0x18] + comp_idx*8) = new_block_offset`.
5. **Re-emit the file-backup region** at the new `primary_tail`.
   The backup region carries a full copy of the live blocks plus a
   set of mirror header fields, so it grows when the primary
   region grows. Its internal structure is partially documented
   in 0013 — it begins with a `77 F6 FF FF FF FF FF FF` sentinel
   (= `-(prim_tail + 9)`-ish anti-marker) and ends with the magic
   `BB BB BB BB`.

## Implementation sketch — `dcf.ReplaceBody` size-changing path

The minimum write strategy for a same-name component growing:

```
1.  c           := f.components[n]
2.  oldOff      := c.Offset
3.  oldBlockSz  := c.BlockSize
4.  primTail    := readU64(f.data, 0x28)
5.  tableOff    := readU64(f.data, 0x18)
6.  newBlockSz  := layoutNewBlock(c, newBody)        // body + header
7.  newBlockOff := primTail
8.  newPrimTail := newBlockOff + newBlockSz + footerPad
9.  // Compose the new file: header || data[0x100..oldOff] ||
//   placeholder(oldOff, oldBlockSz + neighbouringPadding) ||
//   data[oldOff+oldBlockSz+padding..primTail] ||
//   newBlock(newBlockOff, newBlockSz, c.meta, newBody) ||
//   regeneratedBackupRegion(newBlockOff, newBlockSz, …)
10. // Patch header: [0x28] [0x30] [0x50] := newPrimTail
//   table[n] := newBlockOff
//   [0x60] [0xa8] [0xb0] := recomputed hashes (TBD — likely
//   not load-bearing for read; experiment confirms whether
//   Dyalog enforces them).
```

The unknowns left for an implementation pass:

- Whether `header[0x60]` / `[0xa8]` / `[0xb0]` are enforced by
  `⎕FREAD`. First attempt: leave them at the original values and
  see if Dyalog rejects the file. If it does, identify the input
  domain by perturbing fields one at a time.
- The exact backup-region layout for a multi-block file. Currently
  decoded only enough to know "it's a copy of the live blocks
  plus mirrored headers"; the byte-exact recipe for regeneration
  is open.
- The "trailing zero footer" between block-end and primary-tail —
  observed as 24 bytes in the grown new-block tail and 152 bytes
  in the orig fresh-write. Probably padding to some alignment
  (multiple of 0x40?) plus a delete-block sentinel; not yet
  pinned down.

## Recovery instructions for future RE sessions

`/tmp/orig.dcf` and `/tmp/grown.dcf` are session-scratch and
disappear on reboot. Regenerate with:

```bash
~/.bin/gritt -l \
  -e "{0::⍬ ⋄ ⎕NDELETE ⍵} '/tmp/orig.dcf'" \
  -e "tie ← '/tmp/orig.dcf' (⎕FCREATE⍠1) 0" \
  -e "r ← 'C' 0 ⎕FPROPS tie" \
  -e "ns ← ⎕NS''" \
  -e "ns.x ← 42" \
  -e "ns ⎕FAPPEND tie" \
  -e "⎕FUNTIE tie"

cp /tmp/orig.dcf /tmp/grown.dcf

~/.bin/gritt -l \
  -e "tie ← '/tmp/grown.dcf' ⎕FTIE 0" \
  -e "ns2 ← ⎕NS''" \
  -e "ns2.x ← 42" \
  -e "ns2.y ← 99" \
  -e "ns2.z ← 'longer string member to force component growth'" \
  -e "ns2 ⎕FREPLACE tie 1" \
  -e "⎕FUNTIE tie"
```

Both files are then byte-diffed (`xxd`, `python3` u64-LE
walkthroughs) to recover further header fields.
